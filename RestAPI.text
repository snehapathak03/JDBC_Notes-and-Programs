REST API (Representational State Transfer):Every Spring Boot application you build will expose REST APIs.

Chapter 1 – What is an API?API stands for Application Programming Interface.Think of an API as a messenger between two applications.
            Real-Life Example:Imagine you're in a restaurant.You → Customer,Waiter → API,Kitchen → Server,Food → Response.
        	Customer -> Waiter(API) -> Kitchen(Server) -> Food(Response).You never enter the kitchen.
            Similarly,Your application never directly accesses another application's database.It communicates through APIs.
            Real World APIs:Examples:Google Maps API,Paytm Payment API,PhonePe API,Razorpay API,Weather API,GitHub API,OpenWeather API.

Chapter 2 – Why APIs?Without APIs Application A CAN Directlt Access Database of Application B.
        	Problems:Security Risk,Tight Coupling,Difficult Maintenance.
        	With APIs Application A ->REST API ->Application B
        	Advantages:Secure,Fast,Scalable,Independent.

Chapter 3 – What is REST?REST stands for Representational State Transfer.REST is an architectural style for	designing web services.
            REST uses HTTP,URLs,JSON.REST Architecture:Client->HTTP Request->REST API->Business Logic->Database->HTTP Response.
	
Chapter 4 – REST Principles:There are 6 REST Constraints.
    	1. Client-Server:Client and Server remain independent.Example:Browser->Spring Boot.
	    2. Stateless:The server remembers nothing between requests.Example:Request 1 :GET /students, Request 2:GET /students/10
	                 Each request is independent.
    	3. Cacheable:Responses can be cached.Example:Google logo.Doesn't download every time.Browser caches it.
    	4. Uniform Interface:Every REST API follows similar URL conventions.Example:GET /students,POST /students,PUT /students/5
	    5. Layered System:Client doesn't know whether response came from Server,Cache OR Load Balancer.
    	6. Code on Demand (Optional):Server may send executable code(JavaScript).

REST APIs are the backbone of modern web and mobile applications.They enable different systems to communicate 
		over HTTP using a standardized architecture.
		
		What is an API?API stands for Application Programming Interface.An API is a bridge that allows two

What is REST?REST stands for Representational State Transfer.It is an architectural style, not a programming 
	language or protocol.It defines rules for designing web services that communicate over HTTP.	

History of REST:REST was introduced by Roy Fielding in 2000 as part of his Ph.D. dissertation.
	Purpose:Create scalable, simple, and maintainable web services.

REST vs API:Many students think REST and API are the same.They are NOT.API:Any communication interface.
	Examples:Java API,JDBC API,Windows API,REST API,SOAP API,REST API.A type of API that follows REST principles.
	Think like this:
	API

	├── SOAP API
	├── GraphQL API
	└── gRPC API

What is a Resource?The most important concept in REST.Everything is a Resource.Examples:Student,Employee,Product,Book,Customer,Order.
	Each resource has a URI.Examples:/students,/products,/books,/employees,/orders.
	Resource=Object stored on the server.	

URI vs URL vs URN:
	URI:Uniform Resource Identifier.Identifies a resource.Example:/students/101
	URL:Uniform Resource Locator.Tells where the resource exists.Example:https://college.com/students/101
	URN:Uniform Resource Name.Only gives the name.Example:urn:isbn:9780134685991	

REST Constraints:A REST API must satisfy six constraints.
	I. Client-Server:Client and server are separate.Browser->Server.Benefits:
	i.Easy maintenance
	ii.Independent development
	iii.Better scalability
	
	II. Stateless:Every request is independent.Example:Request 1 is GET /profile and Server responds.
	Request 2 is GET /orders and Server does not remember Request 1.
	Authentication details (JWT, session, cookie) must be included or otherwise managed.

	III. Cacheable:Responses can be cached.Example:Product list.Instead of requesting every second,Browser stores the response.
	Benefits:Faster response and Less server load.
	
	IV. Uniform Interface:All APIs follow common rules.Example:GET /students,POST /students,PUT /students/10,DELETE /students/10.
	
	V. Layered System:Client doesn't know whether Proxy,Load Balancer,Gateway,Firewall exists.Example:
		Browser
		  ↓
		Load Balancer
		  ↓
		API Gateway
		  ↓
		Server
		  ↓
		Database
		
	VI. Code on Demand (Optional):Server can send executable code.Usually JavaScript.Not commonly used in REST APIs today.

REST Principles:A good REST API should:
	1.Be stateless.
	2.Use HTTP methods correctly.
	3.Return standard HTTP status codes.
	4.Use meaningful URLs.
	5.Return JSON (commonly)
	6.Be cache-friendly where appropriate

HTTP Methods in REST:
	1.GET:Retrieve data.Example:GET /students
	Returns:
		[
		  {
			"id":1,
			"name":"Sneha"
		  }
		]
	2.POST:Create new resource.POST /students
	Body:
	{
	  "name":"Sneha"
	}
	Response:
	{
	  "id":1,
	  "name":"Sneha"
	}
	Status:201 Created
	3.PUT:Replace entire object.PUT /students/1
	{
	  "id":1,
	  "name":"Sneha",
	  "city":"Nagpur"
	}
	Entire object replaced.

	4.PATCH:Update partial object.PATCH /students/1
	{
	  "city":"Pune"
	}
	Only city changes.

	5.DELETE:Delete resource.DELETE /students/1
	Response:204 No Content	

	REST Endpoint:Endpoint=Complete URL to access resource.Example:https://api.company.com/students/100

Request Structure:
		POST /students HTTP/1.1
		Host: localhost:8080
		Content-Type: application/json
		Authorization: Bearer <JWT>
	{

	}

	Content-Type: application/json
	{

	}
	Contains:Status Line,Headers,Body	

Path Parameter vs Query Parameter
	Path Parameter:Used to identify a specific resource.GET /students/10.10 = Student ID
	Query Parameter:Used for filtering, sorting, searching, or pagination.
		GET /students?city=Nagpur
		GET /products?category=Laptop
		GET /students?page=2&size=10	

Request Headers Examples:
		Authorization: Bearer token
		Content-Type: application/json
		Accept: application/json
		User-Agent: Chrome

REST API Naming Best Practices
	Use nouns:/students BUT Don't use verbs:/getStudents
	Use plural names:/products BUT Avoid:/product
	Nested resources:/users/5/orders
	Version APIs:/api/v1/students
	Use lowercase with hyphens if needed:/order-items	

Idempotent vs Safe Methods
	Safe Methods:Do not modify server data.GET,HEAD,OPTIONS.
	Idempotent Methods:Multiple identical requests have the same effect as one.GET,PUT,DELETE,HEAD,OPTIONS .
	Not idempotent:POST  (usually creates a new resource each time)
